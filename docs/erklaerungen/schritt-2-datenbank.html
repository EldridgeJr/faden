Datenbank: Tabellen, Vektoren, Zugriffsschutz

Supabase in Frankfurt mit fünf Tabellen, pgvector und Volltextsuche. Jede Zeile gehört genau einem Nutzer. Postgres prüft das selbst, nicht die App.

01

Was jetzt funktioniert

Faden hat eine Datenbank im Supabase-Projekt faden in Frankfurt. Fünf Tabellen speichern Notebooks, Quellen, Abschnitte mit Embeddings, Chat-Nachrichten und Studio-Inhalte. Jede Tabelle hat zwei Schutzschichten: GRANT legt fest, welche Rolle sie benutzen darf. Row Level Security legt fest, welche Zeilen. Ein Testskript mit zwei Nutzern beweist, dass niemand fremde Daten sieht oder ändert. Die App spricht über Supabase-Clients für Browser und Server mit der Datenbank, und ein Proxy hält den Login frisch.

Es gibt noch keine Login-Seite und keine Oberfläche für Daten. Das Einlesen von Quellen folgt in Schritt 3.

05
Entscheidungen und Alternativen

    

      
Gewählt
Zwei Schichten: GRANT + RLS
„Automatically expose new tables“ ist aus. Jede Tabelle bekommt nur die Rechte, die sie braucht. anon bekommt nichts.
Alternative
Nur RLS, alle Tabellen automatisch freigegeben. Ein vergessenes enable row level security würde dann alles öffnen.

      
Gewählt
Eine Policy pro Operation, Teilabfrage direkt im SQL
notebook_id in (select id from notebooks where owner_id = …). Jede Regel ist dort lesbar, wo sie gilt.
Alternative
Eine Hilfsfunktion wie is_notebook_owner() als security definer. Kürzer, aber eine zusätzliche Funktion, die man absichern muss.

      
Gewählt
text + check für Status und Typ
Neue Werte sind eine Zeile Migration. Werte lassen sich auch wieder entfernen.
Alternative
Postgres-Enum. Die erzeugten Typen wären genauer ('ready' | …), aber Enum-Werte lassen sich kaum entfernen.

      
Gewählt
Zusammengesetzter Fremdschlüssel in chunks
(source_id, notebook_id) muss in sources existieren. Die kopierte notebook_id kann nicht falsch sein.
Alternative
Ein Trigger, der notebook_id setzt. Oder der App vertrauen. Beides ist unsichtbarer als eine Regel im Schema.

      
Gewählt
Migrationen per MCP auf das Cloud-Projekt
Das SQL liegt trotzdem im Repo, mit derselben Versionsnummer wie in der Datenbank.
Alternative
Lokale Supabase mit Docker und supabase db push. Sauberer zum Testen, aber Docker ist nicht installiert.

      
Gewählt
cacheComponents aus
Seiten mit Login rendern pro Anfrage. Das ist das Muster aus dem offiziellen Supabase-Beispiel.
Alternative
Anlassen. Dann muss jeder Cookie-Zugriff hinter <Suspense>. Der Gewinn ist eine statische Hülle, die bei einer Login-App kaum etwas bringt.

      
Gewählt
getClaims() im Proxy
Prüft die Signatur des JWT mit den öffentlichen Schlüsseln des Projekts. Erneuert abgelaufene Tokens.
Alternative
getSession(). Liest nur den Cookie und prüft ihn nicht. Den Cookie kann jeder fälschen.

    

  


  
  

    
06
Was schiefgehen kann

    

      
Sicherheit
Secret Key umgeht RLS
Die Rolle service_role ignoriert alle Policies. Der Key darf nur auf dem Server stehen und nie ein NEXT_PUBLIC_-Präfix tragen. Jede Abfrage mit ihm muss den Nutzer selbst prüfen.

      
Sicherheit
Der Proxy ist kein Schutz
Er erneuert nur das Token. Der Matcher kann Pfade auslassen. Jede Seite und jede Route prüft den Login darum selbst.

      
Sicherheit
Storage-Pfad vom Client
Die Policy prüft nur den ersten Ordner. Der Server muss den Pfad <notebook_id>/<source_id> selbst bauen und darf keinen Pfad aus dem Browser übernehmen.

      
Stille Fehler
update auf fremde Zeilen meldet Erfolg
RLS filtert die Zeile weg. Postgres meldet „0 Zeilen geändert“, aber keinen Fehler. Die App muss prüfen, ob eine Zeile zurückkam, und sonst 404 zeigen.

      
Suche
Der Stemmer kennt nicht jede Form
„Quellen“ und „Quelle“ werden beide zu quell. „verbindet“ bleibt aber verbindet und passt nicht zu „verbinden“. Die Vektorsuche gleicht das aus.

      
Betrieb
Free-Plan pausiert
Nach etwa einer Woche ohne Aktivität pausiert Supabase das Projekt. Vor dem Loom-Video und dem Interview prüfen, ob es läuft.

      
Typen
string statt fester Werte
Der Typ-Generator kennt keine check-Bedingungen. status ist darum nur string. Ab Schritt 3 grenzt Zod die Werte ein.

      
Disziplin
Nie im Dashboard klicken
Jede Schemaänderung kommt als neue Migration ins Repo. Eine Änderung per Klick im Dashboard fehlt im Repo, und dann weichen Repo und Datenbank voneinander ab.
