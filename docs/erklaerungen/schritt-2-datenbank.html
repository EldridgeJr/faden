Was jetzt funktioniert

Faden hat eine Datenbank bei [[supabase|Supabase]] in Frankfurt. Sie hat fünf Tabellen: Notebooks, Quellen, Textabschnitte, Chat-Nachrichten und Studio-Inhalte. Jede Tabelle ist doppelt gesichert. Ein [[grant|Recht (GRANT)]] entscheidet, wer die Tabelle überhaupt öffnen darf. Eine [[rls|Zeilen-Regel (RLS)]] entscheidet, welche Zeilen man darin sieht. Ein Test mit zwei erfundenen Personen zeigt: Niemand sieht oder ändert fremde Daten.

Noch fehlen die Login-Seite und eine Oberfläche, die Daten anzeigt. Beides kommt in den nächsten Schritten.

05
Entscheidungen und Alternativen

    

      
Gewählt
Zwei Kontrollen statt einer
Jede Tabelle hat ein [[grant|Recht]] und eine [[rls|Zeilen-Regel]]. Gäste haben gar keine Rechte.
Alternative
Nur Zeilen-Regeln. Vergisst man sie bei einer neuen Tabelle, steht diese Tabelle für alle offen.

      
Gewählt
Jede Regel steht bei ihrer Tabelle
Man liest eine [[policy|Regel]] genau dort, wo sie gilt. Nichts ist versteckt.
Alternative
Eine gemeinsame Hilfsfunktion für alle Regeln. Kürzer, aber eine Stelle mehr, die man absichern muss.

      
Gewählt
Status als Text mit Prüfung
Nur bestimmte Werte sind erlaubt, etwa „wartet“ oder „bereit“. Neue Werte sind leicht hinzuzufügen.
Alternative
Ein fester Werte-Typ ([[enum|Enum]]). Genauer für TypeScript, aber Werte lassen sich kaum wieder entfernen.

      
Gewählt
Die Datenbank prüft, ob alles zusammenpasst
Die Notebook-ID steht beim Abschnitt und bei der Quelle. Ein [[fk|Fremdschlüssel]] sorgt dafür, dass beide gleich sind.
Alternative
Der App vertrauen. Ein Fehler im Code würde dann still falsche Daten erzeugen.

      
Gewählt
Änderungen direkt im Online-Projekt
Claude spielt die SQL-Dateien über eine [[mcp|MCP-Verbindung]] ein. Die Dateien liegen trotzdem im Repo.
Alternative
Eine Kopie von Supabase auf dem eigenen Rechner. Besser zum Testen, braucht aber [[docker|Docker]].

      
Gewählt
[[cache|cacheComponents]] aus
Die Funktion baut Seitenteile vorab. Bei Seiten mit Login bringt das wenig.
Alternative
Anlassen. Dann braucht jede Seite mit Login zusätzlichen Code für Ladezustände.

      
Gewählt
Den Ausweis immer echt prüfen
getClaims() prüft die Unterschrift des [[token|Ausweises]]. Fälschungen fallen auf.
Alternative
getSession() liest den Ausweis nur, ohne Prüfung. Einen gefälschten würde es glauben.

    

  


  
  

    
06
Was schiefgehen kann

    

      
Sicherheit
Der geheime Schlüssel
Der [[secret|Secret Key]] umgeht alle Regeln. Er darf nur auf dem Server liegen. Nie im Browser, nie auf GitHub.

      
Sicherheit
Der Pförtner schützt keine Seite
Der [[proxy|Proxy]] erneuert nur den Ausweis. Jede Seite muss selbst prüfen, ob jemand angemeldet ist.

      
Sicherheit
Dateipfad vom Browser
Die Regel prüft nur den ersten Ordner im Pfad. Darum baut der Server den Pfad selbst und übernimmt ihn nie vom Browser.

      
Stille Fehler
Ändern ohne Fehlermeldung
Will jemand fremde Daten ändern, passiert nichts. Es kommt aber auch keine Fehlermeldung. Die App muss das selbst merken.

      
Suche
Die Wortsuche kennt nicht jede Form
„Quelle“ findet „Quellen“. „verbinden“ findet „verbindet“ aber nicht. Die Bedeutungssuche mit [[embedding|Embeddings]] gleicht das aus.

      
Betrieb
Das Gratis-Projekt schläft ein
Nach etwa einer Woche ohne Nutzung pausiert Supabase das Projekt. Vor dem Video und dem Interview prüfen.

      
Typen
Status ist nur „irgendein Text“
TypeScript weiß nicht, welche Werte erlaubt sind. Ab Schritt 3 prüft [[zod|Zod]] das.

      
Disziplin
Nie im Dashboard klicken
Jede Änderung kommt als SQL-Datei ins Repo. Sonst passen Repo und Datenbank nicht mehr zusammen.
