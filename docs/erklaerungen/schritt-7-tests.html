Das Wichtigste in 60 Sekunden

Der ganze Schritt in drei Sätzen:

  1. Zwei Arten von Tests prüfen Faden. 193 kleine Tests ([[unittest|Unit-Tests]]) prüfen einzelne Funktionen, ohne Netz, in unter einer Sekunde. 6 große Tests ([[e2e|E2E-Tests]]) klicken in einem echten Browser durch die App, mit echter Datenbank und echtem Modell.
  2. Der wichtigste Test geht den ganzen Weg eines Nutzers. Notebook anlegen, Text einfügen, Frage stellen, Beleg anklicken, eine fremde Frage stellen, alles löschen. Die Tests fanden einen Fehler in der App und drei Fehler in den Tests selbst.
  3. README und Demo machen Faden für Fremde prüfbar. Das README erklärt, was Faden kann, wie es gebaut ist und wo die Grenzen sind. Das Demo-Notebook „Bauhaus“ hat drei Quellen, einen Podcast und Karteikarten.

Mini-Demos

Die Frage: Der Test klickt „Löschen“ und prüft dann: „Die Zeile ist nicht mehr zu sehen.“ Die Prüfung war grün. Trotzdem stand die Quelle noch in der Datenbank. Wie geht das?
Probier das
Was nacheinander passiert · Zeit ab dem Klick auf „Löschen“
    Für Neugierige: Warum findet der Test die Spalte nicht?

    Ein offener Bestätigungsdialog soll die Seite dahinter für Screenreader stummschalten. Radix setzt darum auf alles außerhalb des Dialogs [[ariahidden|aria-hidden="true"]]. Für einen Screenreader gibt es die Seite dann nicht.

    Ein Rollen-[[locator|Locator]] wie getByRole("region", { name: "Quellen" }) sucht so, wie ein Screenreader sucht. Er überspringt also versteckte Elemente. Er findet keine Spalte „Quellen“ und damit auch keine Zeile darin. „Nicht sichtbar“ stimmt dann sofort, auch wenn der Server noch gar nichts gelöscht hat.

    Die Lösung: Erst warten, bis der Dialog zu ist. Er schließt sich nur, wenn das Löschen geklappt hat. Erst danach prüfen. Diese Lücke steckte auch im Kernpfad-Test. Dort fiel sie nicht auf, weil er danach nicht in der Datenbank nachsah.

    Die Frage: Stell dir vor, eine Funktion geht kaputt. Welcher Test merkt es: ein Unit-Test, ein E2E-Test, eine SQL-Prüfung, oder nur du beim Ausprobieren?
    Probier das: Was geht kaputt?
    Für Neugierige: Warum nicht alles mit E2E-Tests?

    Ein E2E-Test ist langsam (Sekunden statt Millisekunden), kostet Geld (OpenAI) und sagt bei Rot nur „irgendwo auf dem Weg“. Ein Unit-Test ist schnell, kostenlos und zeigt auf eine Funktion. Darum: viele kleine Tests für die Logik, wenige große für die wichtigsten Wege. Was Geld kostet oder von fremden Seiten abhängt (Podcast, Webseiten), habe ich live von Hand geprüft.

    06

    Entscheidungen und Alternativen

    Der fette Satz ist die Entscheidung in einem Satz. Darunter steht, warum, und was die Alternative gewesen wäre.

    „Der E2E-Test nutzt echte Dienste, keine Attrappen.“

    Supabase und OpenAI laufen wirklich. Nur so prüft der Test, was zählt: Einlesen, Suche, Streaming und die Prüfung der Belege. Ein Lauf kostet etwa 0,001 $.

    Warum keine [[mock|Mocks]]? Dann wäre der Test grün, auch wenn die echte Suche nichts findet.

    „Der Test prüft Fakten, nicht den Wortlaut.“

    Das Modell formuliert jedes Mal etwas anders. Der Test prüft darum nur: steht „vier Wochen“ drin, gibt es einen Beleg, kommt bei der fremden Frage genau der feste Ablehnungssatz.

    Warum nicht die ganze Antwort vergleichen? Dann wäre der Test oft rot, obwohl alles stimmt ([[flaky|flaky]]).

    „Die Quelle im Test ist erfunden.“

    Eine Stadtteilbibliothek mit Ausleihe „vier Wochen“. Das Modell kann das nicht aus dem Training wissen. Steht es in der Antwort, kam es aus der Quelle.

    Warum nicht ein Wikipedia-Artikel? Den kennt das Modell schon. Dann beweist eine richtige Antwort nichts.

    „Nach dem Löschen sieht der Test direkt in der Datenbank nach.“

    Die Oberfläche kann nicht zeigen, ob die Datei in Storage weg ist. Und die Demo oben zeigt: Die Oberfläche kann sogar täuschen. Der Test liest darum mit dem [[secretkey|Secret Key]] nach, nur lesend und nur lokal.

    Warum nicht der Oberfläche glauben? Genau so blieb ein Fehler im Test lange unbemerkt.

    „Podcast, Karteikarten und Webseiten teste ich nicht im E2E-Test.“

    Ein Podcast kostet Credits bei ElevenLabs und braucht fast eine Minute. Eine Webseite kann sich ändern oder ausfallen. Die Logik dahinter prüfen Unit-Tests. Den ganzen Weg habe ich live mit dem Demo-Notebook geprüft.

    Warum nicht trotzdem? Jeder Testlauf würde Geld kosten und manchmal ohne eigene Schuld rot werden.

    „Keine neuen Unit-Tests in diesem Schritt.“

    Alle Dateien ohne Test rufen vor allem Datenbank oder APIs auf. Ihre reine Logik ist schon ausgelagert und getestet. Die echte Lücke war der PDF-Weg, und den prüft jetzt ein E2E-Test.

    Warum nicht Supabase nachbauen und alles testen? Viel Code für die Attrappe, und der Test prüft dann die Attrappe statt der echten Datenbank.

    „Der Demo-Zugang ist privat.“

    Es gibt keine Registrierung. Die Zugangsdaten gehen mit der Abgabe an die Prüfer. So kann kein Fremder Kosten verursachen oder die Demo löschen.

    Warum nicht im README? Dann könnte jeder hochladen, löschen und das Budget aufbrauchen, bis zum [[ratelimit|Rate Limit]].

    07

    Was schiefgehen kann

    Testlücke

    Nicht alles läuft automatisch

    Podcast, Karteikarten, Webseiten als Quelle und „Umbenennen“ hat kein E2E-Test. Die Logik prüfen Unit-Tests. Podcast, Karten und Webseite habe ich live mit dem Demo-Notebook geprüft. Geht dort etwas kaputt, merkt es nur ein Mensch.

    Qualität

    Der Test kann ohne eigene Schuld rot werden

    Das Modell antwortet einmal anders, oder das Netz hakt. Darum prüft der Test nur Fakten. Nach den Korrekturen waren alle Läufe grün: siebenmal der Kernpfad, zweimal alle Tests hintereinander.

    Kosten

    Jeder Lauf ruft OpenAI auf

    Etwa 0,001 $. Wichtiger: Pro Lauf zwei Fragen, das [[ratelimit|Rate Limit]] erlaubt 10 pro Minute. Mehr als fünf Läufe pro Minute werden rot.

    Betrieb

    Die Tests laufen nur auf meinem Rechner

    Sie brauchen den Testnutzer und den Secret Key aus .env.local. Auf GitHub laufen sie nicht. Vor jedem Push starte ich sie selbst.

    Betrieb

    Tests nutzen die echte Datenbank

    Es gibt nur ein Supabase-Projekt. Der Testnutzer ist ein eigenes Konto, [[rls|RLS]] trennt seine Daten. [[aftereach|afterEach]] räumt auf. Bricht man einen Lauf hart ab, bleibt vielleicht ein Notebook „E2E …“ beim Testnutzer liegen.

    Sicherheit

    Gespeicherte Sitzung und Secret Key

    Die Datei mit den [[cookie|Cookies]] könnte sich als Testnutzer anmelden. Darum steht sie in .gitignore. Der Secret Key bleibt im Testprozess, er kommt nie in den Browser.

    Sicherheit

    Das Demo-Passwort wird geteilt

    Prüfer bekommen es privat. Es ist neu und nur für dieses Konto. Nach der Bewertung ändere ich es oder lösche das Konto. Bis dahin begrenzen die Rate Limits die Kosten.
